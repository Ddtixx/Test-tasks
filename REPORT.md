# Отчёт по тестовому заданию

## 1. Что сделано

- Развёрнута VM с Ubuntu 24.04 LTS (провайдер Aeza)
- Установлен Nginx, отдаёт статическую страницу
- Настроен ufw: снаружи открыты только 22/tcp и 80/tcp
- Написан Bash-скрипт проверки доступности с логированием
- Скрипт запускается через cron каждые 5 минут (две проверки: локальная и публичная)
- Всё автоматизировано через Ansible, лежит в git-репозитории

## 2. Ручная настройка — основные команды

Делал вручную, чтобы понять, что автоматизировать.

# Установка Nginx

```bash
sudo apt update
sudo apt install -y nginx
sudo systemctl enable --now nginx```

# Проверка
```bash
curl -I http://localhost/```

# Задать кнфигурацию для фаервола
```bash
sudo ufw allow 22/tcp  
sudo ufw allow 80/tcp    
sudo ufw enable          
sudo ufw status verbose```

# Установка скрипта через install
```bash
sudo install -m 0755 check_nginx.sh /usr/local/bin/check_nginx.sh```

## 3. Автоматизация через Ansible

Playbook: playbook.yml

   Структура ролей:

   ufw — firewall: разрешает SSH и HTTP, входящий по умолчанию запрещён.

   nginx — установка и настройка веб-сервера.

   check_script — установка скрипта проверки и cron-заданий.

Почему Ansible:

   Идемпотентность. Повторный прогон не меняет систему.

   Воспроизводимость. Разворачивается одной командой на любой VM.

   Читаемость. Каждая роль — одна задача.

## 4. Bash-скрипт
Файл: roles/check_script/files/check_nginx.sh
Что делает:

   Делает HTTP-запрос к URL (по умолчанию http://127.0.0.1/).

   Сравнивает код ответа с ожидаемым (200).

   Пишет в лог строку: SUCCESS или FAILURE с датой, временем, кодом, URL.

   Возвращает 0 при успехе, 1 при ошибке.

Ключевой момент:
${URL:-http://127.0.0.1/} — параметризация через переменную окружения с дефолтом. Один скрипт — разные проверки

## 5. Работа с ИИ

# Где применял
В разработке файлов отчета и README, в написании черновика скрипта, а так же в разработке структуры плейбука.

# Ошибки при работе с ИИ
1. Неправильный порядок при конфигурировании ufw - сначала enable, потом allow (привело бы к потере доступа к VM)
2. Неправильно интерпретировал задание для скрипта сбора ответа HTTP, предложил только через local ip, я же добавил возможность собирать и через внешний ip
3. Баг http_code=000000 в скрипте

ИИ предложил такую конструкцию для получения HTTP-кода:
```bash
http_code=$(curl -s -o /dev/null -w "%{http_code}" \
    --max-time "$TIMEOUT" "$URL" 2>/dev/null || echo "000")```
При недоступности сервера в логе появлялось http_code=000000 вместо 000.
Причина: curl сам выводит 000 при неудаче подключения. А || echo "000" добавляет ещё один 000 — итого 000 + 000 = 000000. Когда Nginx жив, curl возвращает 200 и || не срабатывает — баг не виден. Как обнаружил: остановил Nginx, запустил скрипт, посмотрел лог —
http_code=000000. Сначала не понял, откуда шесть нулей. Посмотрел на строку с curl — увидел || echo "000". Понял, что curl уже сам выводит 000, и echo добавляет второй.
Исправил:
```bash
http_code=$(curl -s -o /dev/null -w "%{http_code}" \
    --max-time "$TIMEOUT" "$URL" 2>/dev/null || true)
http_code="${http_code:-000}"```

4. --check для роли с установкой пакетов.

ИИ предложил проверять playbook через --check (dry-run). Запустил — Ansible упал на таске запуска Nginx:

Could not find the requested service nginx: host

Причина: в check-режиме apt install не выполняется по-настоящему. Пакет не устанавливается, сервиса nginx.service в системе нет. Модуль systemd пытается найти сервис и падает.
